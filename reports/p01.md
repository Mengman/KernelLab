# P01：GPU 数据搬运与 FMA 吞吐量实验

## 1. 实验目的与当前状态

本实验测量 CPU 与 GPU 之间的 H2D、D2H 复制，以及同一 GPU 内部的 D2D 复制，并观察 grid 大小对逐元素乘加 kernel 的影响。计算任务为 `c[i] = a[i] * b[i] + c[i]`。

本文整理自本次学习过程中提供的终端实测输出及当前代码。4090D 已有结果，GB10 未测。本文作为报告写法演示，缺失的数据明确标记，未用估算代替实测。

环境信息和设备 JSON 已补齐，完整构建及 30 项 FMA 正确性测试已复验通过。4090D 部分达到 P01 当前要求，GB10 保留“未测”；FMA 原始耗时建议后续补充。

## 4. 测量方法与计算口径

每个规模和配置预热 20 次，正式测量 100 次。CUDA Event 的 start、被测操作和 stop 提交到同一默认 stream；等待 stop 完成后读取毫秒耗时。预热结束后同步，内存分配、初始化、结果回读和检查不计入测量。

H2D、D2H 的 CPU 缓冲区使用 `cudaMallocHost` 固定页内存，设备缓冲区使用 `cudaMalloc`。复制使用 `cudaMemcpyAsync`。D2D 使用同一 GPU 的两块独立显存。各轮重复使用相同缓冲区，因此缓存状态可能影响结果。

统计函数按 nearest-rank 计算第 50 百分位，并将其作为本文的中位耗时：100 个样本排序后取第 50 个值，即下标 49；不是中间两个值的平均数。最小耗时取 100 次测量中的最小值。

输入容量使用 MiB：`1 MiB = 2^20 bytes`。带宽使用十进制 GB/s：`1 GB = 10^9 bytes`。

```text
有效复制带宽（GB/s）= bytes / (median_ms × 10^6)
FMA 吞吐量（GFLOP/s）= 2 × n / (median_ms × 10^6)
```

D2D 表格采用 `bytes / 时间`，表示复制的数据量。若分析源读取与目标写入合计流量，则使用 `2 × bytes / 时间`，两种口径不能混用。

FMA 使用 float、grid-stride loop，每个 block 固定 256 个线程，grid 分别为 2、32、128、256、512 个 block。输入规模表示每个数组大小；三个数组总容量为该规模的三倍。每次执行前将初始 c 从 CPU 复制回 GPU，这次复制在 start 事件之前，不计入 kernel 耗时，但会影响缓存状态。最后一次 kernel 的输出与一次 CPU reference 比较。

## 5. 正确性验证

FMA 正确性测试包含 15 种长度：0、1、2、31、32、33、255、256、257、511、512、513、1024、1025、100003。每种长度分别使用固定输入和随机输入，共 30 项；迁移后的测试已由实验者在 4090D 上验证通过。空输入仍启动 kernel，但循环不访问数组；小输入和非整齐长度用于检查边界处理。

随机输入使用 `mt19937`，种子 2026，范围 [-10, 10]。逐元素容限为：

```text
abs(CPU - GPU) <= 1e-5 + 1e-5 × abs(CPU)
```

FMA benchmark 也使用随机输入并逐元素比较。当前不测试 NaN/Inf，因此正确性结论限定于本实验的有限数输入。

D2H、D2D 在计时后逐字节验证目标数据为初始化值 1；实验者报告检查通过。CUDA API 错误由 CUDA_CHECK 检查，kernel 启动错误与同步时的执行错误分别检查。未记录 Compute Sanitizer 检查结果，普通数值测试不能替代工具对越界的检查。

## 7. FMA 吞吐量结果

以下为基于中位耗时计算的实测吞吐量，单位均为 GFLOP/s。原始输出未包含最小耗时和中位耗时，需要后续补充，本文不反推耗时并冒充原始测量。

| 每个数组大小 | 元素数量 n | 2 blocks | 32 blocks | 128 blocks | 256 blocks | 512 blocks | GB10 |
|---|---:|---:|---:|---:|---:|---:|---|
| 1 MiB | 262144 | 6.69008 | 43.2295 | 59.7956 | 59.5782 | 59.3623 | 未测 |
| 16 MiB | 4194304 | 7.40959 | 114.975 | 306.243 | 452.753 | 388.361 | 未测 |
| 256 MiB | 67108864 | 3.89562 | 50.8653 | 112.030 | 119.041 | 118.805 | 未测 |

1 MiB 在 128 个 block 后基本稳定；16 MiB 在本次采样中以 256 个 block 最快；256 MiB 的 256、512 个 block 基本持平。不能据此断言 256 是所有规模和 GPU 的最佳配置。

对于 256 MiB，将 grid 从 2 增加到 256，吞吐量从 3.89562 提升到 119.041 GFLOP/s，约提高 30.6 倍。原因是 grid-stride loop 虽能覆盖所有元素，但只有两个 block 时参与工作的 SM 数量有限。

每个元素执行 2 FLOP，同时读取 a、b、c 并写回 c，按 float 估算访问量为 16 字节，算术强度为 `2 / 16 = 0.125 FLOP/byte`。256 MiB、256 blocks 的吞吐量对应约 `119.041 × 8 = 952.328 GB/s` 的算法访问带宽，支持大输入受到内存访问限制的解释；实际显存流量仍需工具确认。

16 MiB 的三个数组合计 48 MiB，其吞吐量明显高于 256 MiB。缓存收益是可能解释，目前仅为推测。这里测的是逐元素乘加程序的实际吞吐量，不是一个充分复用寄存器数据的计算峰值测试，因此不与规格表 FP32 TFLOPS 直接判断达标与否。

## 8. 实验结论与补充事项

本实验说明，CPU/GPU 数据搬运、GPU 内部复制和逐元素计算有不同的性能限制。输入规模、缓存状态与启动配置会改变实测结果；有效带宽不是硬件的固定规格。

FMA 使用 grid-stride loop 后可以处理空输入、小输入及超过线程总数的输入；扩大 grid 显著改善大输入性能，但增加到一定程度后收益趋于稳定。

# KernelLab 文档写作规范

本文件给后续维护项目文档的 AI 和开发者使用。目标是让读者能够直接开始做题，而不是先猜术语或猜作者想表达什么。

## 1. 总体原则

1. **先说目的，再说术语。** 先回答“这题要学会什么、为什么做”，再介绍实现细节。
2. **用普通话解释技术。** 可以保留英文术语，但第一次出现时必须用一句中文解释。
3. **任务必须能开始执行。** 读者看完题目后，应知道先运行什么、改哪些文件、输入是什么、完成标准是什么。
4. **正确性优先于性能。** 每道涉及 CUDA 的题，都先要求 CPU reference 和 GPU baseline，再谈优化。
5. **数字必须有口径。** 报告性能时必须写 GPU、输入规模、数据类型、warmup、iterations、计时方法和编译参数。
6. **允许失败，但不能假装成功。** 没有实测的 GPU、B200 专属功能或不支持的工具，必须写“未测”或“当前环境不支持”。

## 2. 术语规则

- 缩写第一次出现要写全称并解释。例如：H2D（host to device，即 CPU 内存复制到 GPU）。
- 不要只写“优化访存”“提高吞吐”“减少开销”。必须说明具体做法和可观察指标。
- “性能账本”只能作为通俗称呼，并在首次出现时说明它就是性能记录表。
- “FMA throughput”要解释为实际 FMA kernel 的 GFLOP/s；同时说明它不是 GPU 的理论峰值。
- “occupancy”要说明是 SM 上驻留线程数相对硬件上限的比例，并提醒高 occupancy 不一定更快。
- 对 TMA、TMEM、CLC、TIRx、FA4 等缩写，必须说明它解决的问题、所需硬件以及当前机器是否支持。
- 同一概念在全文中使用同一个名字，不要在“显存、设备内存、GPU memory”之间无说明地来回切换。

## 3. 作业说明的固定结构

每个作业说明尽量按下面顺序写：

### 你要学会什么

用 1–3 句话说明本题的学习目标，以及它和前一题、最终 Tiny Transformer 的关系。

### 开始前

写明需要阅读的章节、需要的 GPU/Toolkit、构建命令，以及没有对应硬件时的替代方案。

### 按步骤完成

使用编号列表。每一步只表达一个动作，尽量包含：

- 要运行的命令；
- 要创建或修改的文件；
- 输入规模、数据格式或边界规则；
- 需要保存的输出。

避免只写“实现一个高效 kernel”或“分析性能”这种无法直接执行的句子。

### 完成标准

用可检查的条件描述完成状态，例如：

- CPU 和 GPU 结果一致；
- 覆盖空输入、边界尺寸和非对齐尺寸；
- 报告包含中位数、最小值和计时方法；
- 另一张没有运行的 GPU 标记为“未测”。

### 常见问题

列出 2–5 个初学者可能遇到的错误，并给出判断方法或排查方向。

## 4. 性能实验写法

性能结果至少要说明：

- GPU 型号和 compute capability；
- 操作系统、CPU 架构、驱动、CUDA Toolkit、编译器；
- 输入 shape、数据类型和数据量；
- warmup 次数和正式迭代次数；
- 使用 CPU 计时、CUDA Event 还是 profiler；
- 报告中位数；如果讨论尾延迟，再报告 p95 或最大值；
- 吞吐的计算公式，例如 GB/s 或 GFLOP/s 如何得到。

不要把一次运行结果写成“GPU 性能就是这个数”。应使用“在本输入和本计时方法下测得”。

## 5. 语言和格式

- docs/ 内的学习计划、作业说明和报告模板可以使用中文，面向当前学习者。
- docs/ 之外的项目文档继续使用英文，除非用户另有要求。
- 代码、命令、文件名、API 名称保持原样，不要为了中文化而改名。
- 代码块必须能复制运行；命令中的路径、preset 和目标名称要与项目实际一致。
- 标题描述具体内容，避免使用“相关说明”“高级内容”“性能优化”等空标题。
- 少用口号和营销式表达，不写“充分发挥 GPU 潜力”“极致性能”等无法验证的句子。
- 不要为了显得专业而堆砌缩写；如果一个术语不是完成任务所必需，可以不引入。

## 6. AI 修改文档前的检查清单

在提交文档修改前，逐项检查：

- [ ] 读者是否知道这篇文档解决什么问题？
- [ ] 所有关键缩写是否在第一次出现时解释？
- [ ] 读者是否知道第一步做什么？
- [ ] 是否列出了文件、命令、输入和完成标准？
- [ ] 是否区分了必须完成、选作和硬件限制？
- [ ] 性能数字是否有完整实验口径？
- [ ] 是否避免把未实测结果写成事实？
- [ ] 是否保持 docs/ 中文、其他文档英文的范围约定？
- [ ] 是否检查了链接、路径和命令与当前工程一致？

如果无法满足某一项，应在文档中明确说明原因，而不是用模糊措辞掩盖。
